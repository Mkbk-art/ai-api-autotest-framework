# 统一断言引擎设计

## 1. 模块位置与目标

Stage 3 的正式实现位于 `core/assertion_engine.py`。它继续解决 Stage 2 已确认的三个问题：断言类型有限、失败信息不够具体、未知断言可能被忽略。

## 2. 兼容旧 YAML

```yaml
- contains:
    status_code: 200
    msg: 登录成功
- eq:
    success: true
- ne:
    success: false
```

## 3. 已验证断言

| 类型 | 示例 | 说明 |
|---|---|---|
| `status_code` | `status_code: 200` | HTTP 状态码 |
| `exists` | `exists: $.data.token` | JSONPath 存在 |
| `not_exists` | `not_exists: $.error` | JSONPath 不存在 |
| `eq` / `ne` | `eq: [$.data.id, 1]` | 相等/不等 |
| `contains` | `contains: [$.msg, success]` | 子串包含 |
| `in` / `not_in` | `in: [$.role, [admin, owner]]` | 集合判断 |
| `gt/gte/lt/lte` | `gt: [$.count, 0]` | 数值比较 |
| `header_eq` | `header_eq: [Content-Type, application/json]` | 响应头精确相等 |
| `header_contains` | `header_contains: [Location, /page/notfound]` | 响应头包含片段；用于兼容相对/绝对重定向地址 |
| `response_time_lt` | `response_time_lt: 1.0` | 响应时间阈值 |

## 4. 失败策略

一条用例内会收集所有失败断言，最终统一抛出 `AssertionError`。错误文本包含断言类型、selector、expected 和 actual，便于 JUnit/Allure 定位。

未知断言类型直接失败。例如当前使用 `db_eq` 会得到 `unsupported assertion type`，避免尚未实现的数据库能力被误认为已经执行。

## 5. 后续扩展

Stage 4/4.5 已接入真实短链接业务响应契约，并新增 `header_contains` 服务 notfound/回收状态的重定向断言；Stage 5 再实现 JsonSchema、MySQL、Redis 等断言。数据库和缓存断言必须使用真实服务与真实查询结果，不复用基线 Demo 返回值。
