# 当前框架执行流程

## 1. 普通声明式 Case

```text
run.py
↓
ConfigManager
↓
pytest
↓
根 conftest.py
├─ 读取 test_selection.include_suites
├─ 扫描当前项目 V2 YAML
├─ CaseRegistry
├─ 动态注册 level/tags marker
└─ 将 declarative Case 参数化给唯一 testcases/test_yaml_cases.py
     ↓
CaseExecutor
├─ ensure requires Context Provider
├─ before_case Hook
├─ ApiRunner
│   ├─ RequestClient
│   ├─ VariableContext
│   ├─ Extractor
│   └─ AssertionEngine / MySQL / Redis
├─ after_response Hook
└─ teardown Hook
     ↓
Pytest Result / JUnit / Allure
```

项目新增普通 Case 时只增加 YAML，不增加 `test_xx.py` wrapper。

## 2. 复杂 Workflow

```text
pytest
↓
projects/testcases/<sut>/workflows/*.py
↓
Python 只负责控制流
↓
CaseExecutor / CaseRegistry
↓
复用 YAML Case / YAML Assertion Group
↓
ApiRunner
```

复杂 Workflow 的判断依据不是“项目复杂”，而是测试本身是否存在分支、循环、多状态生命周期、异常补偿或 finally cleanup。

## 3. Context Provider

`requires` 表示 Case 所需的项目上下文，例如：

```yaml
requires:
  - project.authenticated
```

Provider 可以一次实现登录、临时资源或租户准备，并由多条 YAML Case 复用。Core 只认识 Provider 名称和生命周期，不认识业务。

## 4. 失败与 cleanup

CaseExecutor 保证声明了 teardown 的写操作在成功和失败路径都尝试 cleanup。这样即使 HTTP 已经创建资源、后续 DB/Redis 断言失败，也不会因为断言异常直接跳过项目清理。

## 5. 当前项目隔离

环境 YAML：

```yaml
test_selection:
  include_suites:
    - <project>
```

决定本次只扫描哪个项目。公共 `conftest.py` 不写死 Shortlink 或 Demo 名称。
