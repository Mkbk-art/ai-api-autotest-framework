# AI 失败分析基础与 Failure Triage 目标设计

## 1. 当前定位

当前仓库已经具备第一代 Evidence-based AI Analysis 基础：

```text
run.json + junit.xml
↓
FailureEvidence
↓
Deterministic Facts
↓
Sanitizer
↓
AI Client
↓
Strict JSON / Validator
↓
ai-analysis/*
```

这一层继续保留，因为它证明了：

- AI 不参与 Pytest PASS/FAIL；
- Evidence 在发送 Provider 前脱敏；
- 模型结论必须引用真实 Fact ID；
- 模型不可用、超时、非法输出均安全降级；
- 原始 run.json / junit.xml 不被模型修改。

但“把单个 traceback 换一种说法”不再作为最终 AI 卖点。最终目标升级为：

> **Evidence-based Failure Triage：先确定性分类、再聚类，只有复杂/模糊问题才调用 AI。**

---

## 2. 当前 AI Provider 配置

### 普通用户

`config/ai.yaml` 是真实主配置。完全不使用 Git 的用户可以直接填写自己的 Provider/Model/Key。

### Git 开发者

公开/团队仓库推荐使用：

```text
config/ai.local.yaml
```

该文件由 `.gitignore` 保护，不进入 GitHub。

### 配置优先级

```text
CLI 临时覆盖
> config/ai.local.yaml
> 主 YAML（project ai.yaml；项目没有才使用 Home ai.yaml）
> AI_* ENV fallback
```

### Provider / Protocol

Provider 只是配置 Profile 名，Production Python 只按 `protocol` 选择 Adapter：

```text
AIProviderConfig
↓
AIClientFactory
↓
Protocol Adapter
```

第一版协议：

```text
openai_chat_completions
```

同协议新增 Provider 不修改 Python。

---

## 3. API Key 安全

CLI 不提供：

```text
--api-key VALUE
```

只允许：

```text
--api-key-prompt
```

避免 Key 出现在 shell history / process list。

日志、Artifact、异常文本和 dataclass repr 都不能输出 Key。

---

## 4. 当前独立分析入口

```bash
python -m ai.cli analyze --run-dir reports/runs/<run_id> --no-ai
```

这条命令只构造确定性 Evidence，不调用模型，适合检查脱敏和 Facts。

配置 Provider 后：

```bash
python -m ai.cli analyze --run-dir reports/runs/<run_id>
```

当前该独立 CLI 仍保留，未来即使 CI 自动触发 Triage，它也可以用于重新分析某次历史 Build。

---

## 5. 当前输出契约

模型输出必须是严格 JSON：

```json
{
  "hypotheses": [
    {
      "title": "non-empty string",
      "confidence": "low",
      "evidence_refs": ["F1"],
      "reasoning_summary": "non-empty string"
    }
  ],
  "next_checks": [
    {
      "priority": 1,
      "action": "non-empty string",
      "evidence_refs": ["F1"]
    }
  ],
  "uncertainties": []
}
```

当前 Validator 继续作为下一代 Failure Triage 的安全基础。

# 6. 下一代 Failure Triage

## 6.1 Evidence 扩展

下一阶段不再只看 JUnit，还会读取已脱敏的 Allure 结果：

```text
run.json
JUnit
Allure result.json
Request attachment
Response attachment
Assertion failure
Network / data-source error
Case metadata
operation_id
dependency metadata
```

---

## 6.2 单个失败

单个失败并不自动调用 LLM。

```text
Single Failure
↓
Deterministic Classifier
↓
已经明确？
├─ YES -> 直接输出分类/建议
└─ NO  -> AI Triage
```

确定性即可处理的典型情况：

- Connection refused；
- DNS / timeout；
- 明确缺 Token；
- 已知数据库连接失败；
- 单纯、无歧义的断言差异。

只有多个证据信号冲突或难以从规则判断根因时，才调用 AI。

---

## 6.3 多个失败

```text
N Failures
↓
Failure Fingerprint
↓
Cluster
↓
Known Failure Classification
↓
Ambiguous Cluster
↓
AI Triage
```

目标不是“解释 18 次错误”，而是把：

```text
18 failed tests
```

压缩为类似：

```text
Authentication dependency  12
Redis connectivity           4
Business behavior            2
```

测试人员优先排查 3 个问题，而不是逐条打开 18 个 Case。

---

# 7. Allure 集成目标

不建设第二套 AI Dashboard。

目标执行链：

```text
allure-results-raw
↓
Failure Evidence / Cluster / AI Triage
↓
allure-results-enriched
↓
Allure HTML
```

最终失败 Case 的 Allure 详情可以包含：

```text
Request
Response
Assertion
Failure Cluster
AI Triage
Evidence refs
Suggested checks
```

Raw Allure Result 保持不可变；AI 不修改测试状态，也不覆盖 Pytest exit code。

---

# 8. AI 的最终位置

整个项目最终只在三个真正需要智能推理的位置使用 AI：

```text
Before Test
Coverage Gap -> Risk-based Test Design

Before Regression
Deterministic Impact -> AI Semantic Impact Supplement

After Test
Failure Cluster -> Ambiguous AI Triage
```

Contract Diff、Coverage、直接依赖、Assertions、PASS/FAIL、Known Failure Classification 尽量由确定性代码完成。
