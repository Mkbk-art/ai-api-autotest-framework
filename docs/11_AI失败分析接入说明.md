# AI 失败分析接入说明

## 1. 定位

Stage 7.1 给项目增加的是**可选 AI 失败解释能力**，不是新的测试判定器。

现有主链仍然是：

```text
run.py
→ Pytest
→ AssertionEngine
→ JUnit / Allure / run.json
→ 原始 PASS / FAIL
```

AI 链路只在测试已经结束后读取 Artifact：

```text
run.json + junit.xml
→ FailureEvidenceBuilder
→ 确定性 Facts
→ 脱敏
→ 可选 AIClient
→ 严格输出校验
→ ai-analysis/*
```

因此没有模型、模型超时、模型返回非法 JSON，都不会改变原测试结论。

## 2. 输入证据

第一版只依赖每次运行已有的：

```text
reports/runs/<run_id>/run.json
reports/runs/<run_id>/junit.xml
```

`FailureEvidenceBuilder` 先由 Python 确定性地提取：

- `run_id`；
- environment / level；
- 原始 `pytest_exit_code`；
- failure/error 数量；
- 每条 failure/error testcase；
- 连续编号的 `F1/F2/...` Facts。

AI 不能创建或修改 Facts，只能引用这些 Fact ID 做假设和排查建议。

## 3. 本地无 AI 模式

最适合首次验证和公共 CI 的方式：

```bash
python -m ai.cli analyze \
  --run-dir reports/runs/<run_id> \
  --no-ai
```

即使没有任何模型 Key，也会生成：

```text
reports/runs/<run_id>/ai-analysis/evidence.json
reports/runs/<run_id>/ai-analysis/analysis.json
reports/runs/<run_id>/ai-analysis/analysis.md
```

此时 `analysis.json` 中：

```json
{
  "ai_status": "unavailable"
}
```

表示“确定性证据生成成功，但本次没有调用模型”，不是测试失败。

## 4. OpenAI-compatible Provider

Stage 7.1 的 production code 不绑定某个厂商 SDK，真实 Provider 通过通用 HTTP Adapter 接入。

只从运行环境/Secret Store 读取：

```text
AI_API_BASE
AI_API_KEY
AI_MODEL
AI_TIMEOUT
```

`.env.example` 只保存注释化占位示例，不保存真实 Key。

配置完成后：

```bash
python -m ai.cli analyze --run-dir reports/runs/<run_id>
```

若 Provider 配置不完整，框架自动退化为 `ai_status=unavailable`。

## 5. 输出 Artifact

### `evidence.json`

只包含确定性、已脱敏事实，是 AI 输入的可审计副本。

### `analysis.json`

包含：

```text
facts
hypotheses
next_checks
uncertainties
ai_status
```

每条 hypothesis/next_check 必须通过 `evidence_refs` 引用真实 `F#`。

### `analysis.md`

只渲染已经通过 Validator 的结果，方便 Jenkins Artifact 或本地直接查看。

## 6. 安全边界

Stage 7.1 复用唯一的 `utils/sanitizer.py`：

1. 结构化字典先遮蔽 Authorization、Cookie、password、token、API Key 等字段；
2. JUnit/异常自由文本再通过 `sanitize_text()` 处理 Bearer Token、key=value 凭据、Cookie、邮箱和常见大陆手机号；
3. 文本先脱敏，再截断；
4. Provider API Key 不写日志、不写 Prompt Artifact、不写 `run.json/evidence.json/analysis.json`；
5. Provider 异常只保存 `error_type`，不保存 `str(exc)`，避免第三方异常回显敏感 Header/URL。

这是面向当前接口测试框架的最小安全边界，不声称替代企业级 DLP。

## 7. 降级

支持四种稳定状态：

```text
success               模型输出通过结构与 Fact 引用校验
unavailable           未配置 AI Client/Key
error                 模型网络/运行时调用失败
invalid_model_output  非法 JSON、非法结构或引用不存在的 Fact
```

后三种都仍保留 `evidence.json`，并且不会修改原始 `run.json/junit.xml` 或 Pytest exit code。

## 8. 真实历史故障验证

Stage 7.1 没有虚构“看起来真实”的故障，而是把项目开发过程中真实发生过的问题泛化、脱敏成 fixture：

1. **共享认证前置失败**：一个直接登录 failure 导致多个依赖认证 fixture 的 setup error，用于验证 AI 能把连锁错误看作共同阻塞，而不是多个独立 Bug；
2. **Jenkins 历史 JUnit 污染**：当前 Pytest 已通过但 Jenkins 因宽泛报告 glob 变为 UNSTABLE，用于验证事实可以区分“测试成功”和“CI 报告聚合异常”。

测试 fixture 不保留真实账号、密码、Token、短链接 URL 或真实数据表信息。

## 9. 与真实 SUT 的关系

`ai/` production code 不包含：

```text
/api/short-link
shortlink-local
nurl.ink
Shortlink 表名
Shortlink Redis Key 前缀
```

Shortlink 继续只是当前已经真实验证的 Project Adapter/Test Cases 示例。未来换成订单、支付、用户中心等 SUT，AI 失败分析仍然读取统一 `run.json + junit.xml`，无需修改 AI Core。

## 10. 当前验收边界

离线代码验收使用：

- Fake AI Client；
- Fake HTTP Session；
- 历史脱敏故障 fixture；
- Architecture Guard；
- 全量 framework tests；
- 原 `run.py --env test --level smoke` 回归。

在真实 Provider 调用实际成功之前，README/简历只能描述“已实现 OpenAI-compatible Adapter 并完成离线 Fake HTTP 验证”，不能宣称“真实在线模型分析已经验证”。
