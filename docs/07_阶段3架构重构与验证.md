# Stage 3 架构重构与验证

## 1. 目标

Stage 3 不新增真实业务功能，只把 Stage 2 已验证代码迁移为更适合作为个人项目长期维护的正式架构，并通过自动化测试证明迁移没有破坏已有行为。

## 2. 迁移前后

```text
Stage 2                         Stage 3
base/apiutil.py          ->     core/api_runner.py
base/debugtalk.py        ->     utils/debugtalk.py
common/config_manager.py ->     core/config_manager.py
common/request_client.py ->     core/request_client.py
common/variable_context.py ->   core/variable_context.py
common/extractor.py      ->     core/extractor.py
common/assertion.py      ->     core/assertion_engine.py
common/yaml_loader.py    ->     core/case_loader.py
common/logger.py         ->     utils/logger.py
common/sanitizer.py      ->     utils/sanitizer.py
common/jsonpath_util.py  ->     utils/jsonpath_util.py
common/project_paths.py  ->     utils/project_paths.py
common/allure_compat.py  ->     utils/allure_compat.py
testcase/                ->     testcases/
```

`RequestBase` 实现类同步重命名为 `ApiRunner`，因为它的真实职责是编排一条接口测试用例，而不是泛化的“Base”基类。

## 3. 代码说明规范

- 所有 Python 模块均有模块顶部 docstring，说明模块用途和边界；
- `core/`、`utils/`、`run.py` 中公共类和公共函数均有 docstring；
- Pytest fixture 说明自己的生命周期和前置数据职责；
- 复杂逻辑的行内注释解释设计原因，例如精确变量保留类型、Header 的 `None` 删除语义、Allure HTML 不覆盖 Pytest 退出码等；
- 由 `tests/unit/test_stage3_structure.py` 自动检查正式目录和模块说明规范。

## 4. 目录职责

### core

框架主执行链：配置、用例加载、HTTP 请求、ApiRunner、变量上下文、响应提取、统一断言。

### utils

辅助能力：DebugTalk、日志、敏感信息脱敏、轻量 JsonPath、项目路径和 Allure 兼容。

### testcases/demo

只保存 Mock Demo，用来证明框架行为，不代表真实短链接 SaaS 的业务覆盖。

### tests

测试框架自身。Stage 3 新增目录/文档规范回归，防止后续再次出现两套结构或缺失说明。

## 5. 开源归属

保留 MIT `LICENSE` 和 `BASELINE_SOURCE.md`，新增 `THIRD_PARTY_NOTICES.md`，明确：

- 上游基线来源；

- 已完成的缺陷修复和重构；
- MySQL、Redis、真实短链接、CI/CD、AI 等未来能力尚未实现。
