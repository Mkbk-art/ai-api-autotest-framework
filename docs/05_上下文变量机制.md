# 上下文变量机制

## 1. 为什么替换 extract.yaml

基线框架把 Token、interface_id 等变量追加写入共享 `extract.yaml`。这种方式存在文件 IO、重复键、跨用例污染和并发冲突。Stage 2 已将运行时唯一真源改为内存 `core.variable_context.VariableContext`，Stage 3 继续保留该设计并迁入正式 `core/` 架构。

## 2. 核心接口

```python
context.set(key, value, scope="scenario")
context.get(key, scope=None)
context.replace_variables(data)
context.clear(scope=None)
context.export_debug_snapshot()
```

支持 `session`、`scenario`、`case` 三个逻辑作用域。未指定 scope 时按：

```text
case -> scenario -> session
```

查找，因此更具体的 case 值可以覆盖场景级和会话级同名变量。

## 3. 三层作用域的准确含义

- `session`：较长生命周期公共变量的逻辑命名空间，例如未来的 `test_run_id`。
- `scenario`：同一业务链路共享变量，是当前主要作用域，例如 `access_token`、`interface_id`。
- `case`：单条用例临时变量，可覆盖同名 scenario/session 值。

这三个名称**不是 Pytest fixture scope**。当前真正的测试间隔离来自 `testcases/conftest.py` 中 function-scoped `variable_context` fixture：每条业务测试都会创建一个新的 `VariableContext` 实例。

## 4. 类型保留

如果一个字符串只有变量：

```text
${interface_id}
```

且变量值为整数 `7`，替换结果仍然是整数 `7`。

如果变量位于更大的字符串中：

```text
Bearer ${access_token}
```

则替换为字符串。字典、列表和元组会递归替换。

## 5. DebugTalk 与普通变量

旧 YAML：

```text
${get_extract_data(access_token)}
```

继续可用，用于兼容早期 DSL。新用例更推荐直接使用：

```text
${access_token}
```

`VariableContext` 负责“变量存在哪里”，`utils.debugtalk.DebugTalk` 负责“动态值怎样计算”，例如 `${random_string(8)}`、`${future_date(7)}`。
